# Reproducibility — Phase 6

How every Phase 6 number is produced, recorded and re-run. Written
2026-09-12; updated as runs land.

## 1. Where things live

| What | Where | Tracked in git? |
|---|---|---|
| Experiment registry (append-only JSONL, one record per run event) | `artifacts/experiment_registry/registry.jsonl` | yes |
| Benchmark reports (JSON, with CIs and manifest hashes) | `artifacts/benchmark_reports/*.json` | yes (prediction dumps `*.predictions.jsonl` stay on the cluster) |
| Per-run metrics + run metadata | `docs/assets/phase6/<run>/{metrics,run_metadata}.json` | yes |
| Weights | cluster `compute01:~/satquery/checkpoints/v3/<run>/` + local backup `checkpoints/v3/` | **no** (sha256 in the registry) |
| Dataset manifests (unified format) | `data/<dataset>/manifests/{train,val,test}.jsonl` + `stats.json` (sha256 per file) | no (regenerated by `training/prepare/*`; hashes are in the registry) |
| Cluster logs | `compute01:~/satquery/logs/*.log` | no |

`scripts/sync_cluster_results.sh [run ...]` pulls metrics, reports and
registry records from the cluster into the repo. `scripts/backfill_registry.py`
turned the Phase 5 artefacts into registry records once.

## 2. Registry record

Fields (all present, null when unknown): `experiment_id, timestamp,
git_commit, dataset_versions, dataset_manifest_hash, model, architecture,
hyperparameters, training_steps, seed, hardware, duration_s, checkpoint,
checkpoint_sha256, validation_metrics, test_metrics, status, notes`.
A run writes `status=running` at start and `done`/`failed` at the end under
the same id; `registry.load()` returns the latest record per id. Smoke
tests (checkpoints under `/tmp`) are never recorded.

## 3. Unified data format

One JSON object per line::

    {"id": "<dataset>:<stable id>", "image": "rel/path" | "images": [a, b],
     "modality": "rgb|msi|sar", "task": "<VQA>|<GROUNDING>|<CAPTION>|<CHANGE_CAPTION>",
     "question": "...", "target": str | [str, ...] | {"bbox_xyxy": [...], ...},
     "split": "train|val|test", "metadata": {...}, "source": "...",
     "license": "...", "synthetic": false}

Paths are relative to the dataset root (`<root>/manifests/<split>.jsonl`),
so no manifest carries a machine-specific path. Preparers:
`dior_rsvg_official.py`, `rsvqa_official_train.py`, `caption_manifests.py`,
`instruct_mix_manifest.py`. Each writes `stats.json` with row counts,
validator output and the sha256 of every manifest; evaluators copy that
hash into their report.

## 4. Checkpoint policy

* Every trainer writes `run_metadata.json` at start and `metrics.json` at
  the end; VLM trainers keep `adapter_best` (selection metric from
  generation), `adapter_last` (+ `train_state.pt` for resume) and
  `adapter_final`; CNN trainers keep `best.pt` (by val) and `last.pt`/`final.pt`.
* Nothing is deleted by a trainer. Pruning, if ever done, requires: load
  test, sha256 recorded in the registry, independent copy verified.
* Backups: `checkpoints/v3` is rsynced to the local workstation after each
  milestone (`scripts/backup_checkpoints.sh`, to be added with the first
  full backup) and the sha256 of each best checkpoint is in the registry.

## 5. Re-running each Phase 6 number

All commands run on `compute01` from `~/satquery` with
`~/satquery/.conda-env/bin/python`, as `systemd-run --user` units (see
`docs/phase5-full-training.md` §7 for why bare processes die with SSH).

| Number | Command |
|---|---|
| DIOR-RSVG zero-shot / LoRA (official test) | `evaluation/grounding_official_eval.py --base models/qwen25_vl_3b --data data/dior_rsvg_official --arms zero_shot=BASE lora_r16=checkpoints/v3/grounding_vlm_r16/adapter_best --out ...` |
| Grounding adapter | `training/train_grounding_vlm.py --model models/qwen25_vl_3b --data data/dior_rsvg_official --ckpt-dir checkpoints/v3/grounding_vlm_r16 --epochs 1 --batch-size 8 --grad-accum 2 --lr 1e-4 --val-limit 400 --val-every 400` (run as 2 epochs to step 400, resumed with `--epochs 1`; both recorded in the registry) |
| LEVIR-CD change_mask v3 | `training/train_change_mask.py --index data/levircd/index.json --ckpt-dir checkpoints/v3/change_mask --arch v3 --dim 64 --epochs 40 --batch-size 16 --lr 2e-4 --loss bce_dice --augment --cosine --amp --workers 6 --select-on-val` |
| WHU-OPT-SAR fusion v3 | `training/prepare/whu_opt_sar_relabel.py` then `whu_opt_sar_resplit.py`, then `training/train_optsar_fusion_v3.py --index data/whu_opt_sar/index_v2_scene_split.json --ckpt-dir checkpoints/v3/optsar_fusion --epochs 40` |
| RSVQA-LR (official test) | `evaluation/rsvqa_official_eval.py --base models/qwen25_vl_3b --data data/rsvqa_lr_official --arms <name>=<adapter>` (4-bit, the deployed load path) |
| VQA adapter | `training/train_vlm_sft.py --train data/rsvqa_lr_official/manifests/train.jsonl data/instruct_mix_v2/manifests/train_no_rsvqa.jsonl --val ... --epochs 1 --batch-size 16` |
| RSICD / LEVIR-CC (VLM) | `evaluation/vlm_task_eval.py --manifest data/<ds>/manifests/test.jsonl --arms ...` |

Seeds are 42 everywhere unless the registry says otherwise. GPU: NVIDIA
L40S 46 GB, shared; every run records the free VRAM it started with.

## 6. Known non-determinism

* Qwen2.5-VL generation is greedy; bf16 matmuls on a shared GPU can differ
  in the last bits between runs, which moves a box by a pixel occasionally.
  Reported CIs absorb this; exact-match VQA is unaffected in practice.
* DataLoader worker RNGs in the CNN trainers are seeded per process, not
  per worker; augmentation order is not bit-reproducible across worker
  counts. Metrics reproduce to ~0.002.
